## What was built
`src/fetch/{mod,body,dns}.rs`, `src/server.rs`, `src/error.rs`, `src/main.rs`.
- Flow per hop: `validate_target` (scheme, userinfo, IP literal, one lookup, every answer checked) -> URL cross-check -> client built for that hop (HTTP/1.1 only, no pool, no proxy, no cookies, no referer, redirect policy none, `dns_resolver` = `Pinned` = exactly the validated addresses for exactly the validated host) -> GET with `Accept-Encoding: gzip`. Own redirect loop, 5 hops then `too_many_redirects`, `Location` joined with `Url::join` and re-validated as `Origin::Redirect`.
- Body: streamed chunk by chunk, re-sliced to 64 KiB; wire bytes and decompressed bytes both capped at `FETCH_MAX_BYTES`; `Content-Length` over the cap aborts before reading; `Content-Encoding` accepted only absent, `identity` or one `gzip` (checked before decoding); gzip through `flate2::write::GzDecoder` (pure Rust) in steps of at most 32 KiB, first member only, trailing bytes ignored; hand-written UTF-8 streaming decoder with U+FFFD replacement. Nothing accumulates the body; the tool keeps only the requested character window.
- Limits: overall deadline `FETCH_TIMEOUT_MS` (default 15 s) from permit acquisition, covering DNS, connect, TLS, headers, all hops, body; queueing for a slot is bounded by the same timeout; semaphore of 3 (`FETCH_MAX_CONCURRENCY`, already parsed by `Config`); header count 64 (parser) and 32 KiB (names plus values, checked after parse).
- Errors added: `too_large`, `timeout`, `unsupported_encoding`, `http_error`, `too_many_redirects`, `network_error`, `bad_response`, `internal`; `not_implemented` removed. Transport errors are categories only, never an address or port (test).
- TLS: rustls with ring only (installed once), embedded `webpki-roots`, config built lazily on the first https hop. Real https, gzip and a redirect-to-metadata refusal were exercised by hand against example.com and httpbin.org with the release binary (not a CI test).
- Dependencies: reqwest =0.13.5 (`rustls-no-provider`, no default features), rustls =0.23.45 (ring, std, tls12), webpki-roots =1.0.9, flate2 =1.1.9 (rust_backend); tokio =1.53.1 gains `net`, `time`, `sync` (all three used: `lookup_host`, deadline, semaphore). `deny.toml` allows CDLA-Permissive-2.0 (webpki-roots data licence). System allocator unchanged. Release profile unchanged.
- Guard: `scripts/check-release-features.sh` no longer has `HTTP_CLIENT_BAN`, `RAW_NET_BAN`, `check_no_http_client_text`, `check_no_tokio_net_text`, `check_no_http_client`, `--no-http-client` or their self-test blocks. Feature allowlist and marker grep unchanged. CI: new job `a3b-merge-gate` (release profile; fails if a named gate test did not run); `docs/ci-branch-protection.md` updated (six required checks).

## Honest gaps
1. **Native aarch64 RSS smoke NOT done.** This host is x86_64. Substitute (not the AC, not evidence for G4): bench-loopback release build, one 5 MiB HTML fetch from a local Python server, VmHWM read from /proc: idle 3884 kB, after the fetch VmHWM 5760 kB. Needs a run on aarch64 (E-2/E-3 harness).
   - Correction (cleanup, 2026-09-20): now measured on native aarch64: 10/10 valid, median VmHWM 4.77 MiB (advisory, single run, CI run 35523134933); see docs/BENCHMARK.md section 14. The x86_64 figure above is kept as history.
2. **Idle RSS with the client compiled in is unmeasured on aarch64**; the Sprint 1 idle figures in docs/BENCHMARK.md predate the client (text says so). Release binary (x86_64, stripped) is 3.0 MB; not compared with the spike numbers. reqwest's `rustls-no-provider` also compiles `rustls-platform-verifier` (unused at runtime), a small binary and audit-surface cost (ADR-001 note).
3. **TLS is not covered by any automated test** (no offline CA; a fixture-CA feature is not adopted). Certificate validation and webpki-roots were only exercised manually against real sites.
4. **Header byte limit is not the explicit small limit the AC implies at the parser**: reqwest 0.13.5 does not expose hyper's `http1_max_buf_size`, so a head can occupy hyper's default (about 400 KiB) before our 32 KiB post-check refuses it. Count limit (64) is enforced by the parser.
5. No content-type gate (A-6): binary bodies are read up to the cap. No early stop (A-5): a chunked body over the cap is `too_large` even if the window would be complete, as the A-3b AC says. No HTML conversion (A-4), no next-`start_index` footer or clamp message (FR-02/FR-04, A-5), no charsets other than UTF-8 (A-8), no Final-URL header (A-9), errors not yet cause-specific (A-7).
6. A truncated gzip is `bad_response`; a truncated identity body with a short `Content-Length` surfaces as `network_error` (hyper), not a dedicated code.
7. `getaddrinfo` runs on tokio's blocking pool and cannot be cancelled: on timeout the pool thread lingers until the lookup returns. Bounded by the OS resolver timeout.
8. One client (and TLS config clone) is built per hop; the cost was not measured against NFR-02.
9. The `a3b-merge-gate` CI job is new and unproven until the PR run; the owner must add it to branch protection (not configured yet). The source-scan part of the gate is a string search, a tripwire not a proof; the real guarantees are `Pinned` being the only resolver and the zero-connection assertions.
10. Timing-based tests (sleeps up to a few hundred ms, wait loops up to 5 s) ran 5 times in a row without a failure but could flake on a very loaded runner.
11. The MCP tool level is tested end to end only in the `bench-loopback` configuration (loopback is the only offline target); default-config coverage is the client tests plus the refusal cases through the binary.
12. E-7 (50-URL snapshots) not started (list not provided); no conversion work.
13. The `--version` build/commit hash AC from E-8 is still not implemented (unchanged from E-8's report).
