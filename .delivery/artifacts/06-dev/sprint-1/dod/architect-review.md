## Error model and the ADR-006 amendment
- Amending an Accepted ADR with a dated note is the correct mechanism (the decision's intent, model-correctable errors and a stable `error[code]: field: msg` shape, is intact; only the transport for parameter rejections changed). The alternative, a custom `call_tool` bypassing rmcp `Parameters`, would lose schema wiring and add a memory-neutral but fragile hack. I ratify the amendment. Process point: it was made by the developer, not the architect; record architect ratification (this review) and note it in the ADR index.
- `isError: true` for input validation is what current MCP guidance recommends (tool-execution errors so the model can self-correct), and every mainstream client surfaces it to the model. A JSON-RPC invalid-params error is often swallowed or shown as a generic failure. Acceptable.
- One risk to keep visible: clients that only key on JSON-RPC errors will treat these as normal tool output text; the `error[code]` prefix and `isError` flag mitigate. No action.

## Security assessment: `::a.b.c.d` (IPv4-compatible, `::/96`) with public embedded address
Current behaviour: allowed (e.g. `::8.8.8.8`), because ADR-003 says extract the IPv4 and judge it by the v4 table.
Consequence: IPv4-compatible addresses are deprecated (RFC 4291 sec 2.5.5.1); Linux does not route them to IPv4, so a dial to `::8.8.8.8` normally fails or hits an unintended IPv6 path. It cannot reach a private target (private embedded is blocked; `::/128` and `::1` caught earlier). Risk is low but nonzero: exotic stacks/NAT64-like middleboxes could translate it, and the check is judging a different destination than the socket may reach (validation/dial semantic gap), which is exactly the class ADR-003 exists to avoid. There is no legitimate use.
Recommendation: BLOCK all of `::/96` (add one V6 row, category "deprecated IPv4-compatible"; keep `::ffff:0:0/96` mapped, `64:ff9b::/96` NAT64 and `2002::/16` 6to4 as embedded-v4 judged). Cost is zero false positives in practice. Decide in B-2 with an ADR-003 dated note; flagged now as requested.

## Findings (all non-blocking)
- N1 (must close before A-3b; doc): ADR-003 step 1 mandates the `url` crate and architecture 9.1/section 8 (dependency list, "14 of 15", `url = "=2.5.8"` pin, threat item at line 390) still say so. The developer replaced it with a hand-rolled strict parser (WHATWG numeric-IPv4 folding, fail closed on anything ambiguous) and did not amend ADR-003 or architecture. Dropping it saves a direct dependency and is defensible, but a security-critical decision reversal needs a dated ADR-003 amendment plus updated counts (now 4 of 15 planned) and pins.
- N2 (A-3b input): the parser differential is the new risk. A-3b's client (reqwest) will re-parse the URL with the `url` crate; our validated host/port/scheme must equal what the client parses. Only dialling the validated `SocketAddr` set neutralises the address side, but Host header and SNI come from the client parse. `a3b_merge_gate` must include (a) a differential test of `check_url` against `url::Url::parse` over the encodings corpus (dev-dependency only) and (b) a proof that the dial route accepts only `Validated.addrs` (custom connector/resolver, no fallback to the client's own resolver). Nothing at HEAD enforces that a `Resolver` implementer cannot be bypassed; that enforcement is A-3b's gate, as designed.
- N3 (doc): architecture.md line 193 still says "Only parameter validation uses the protocol error path", contradicting the amended 6.1. Fix wording. Also `src/error.rs` variant doc for `InvalidArgument` still says "protocol-level invalid-params error"; fix comment.
- N4 (doc): architecture 14.1 should state that `policy` is a top-level module (see Policy location) and that `Resolver` is a trait returning `Vec<IpAddr>` (async fn in trait), so A-3b's real resolver needs tokio `net` (documented in the dev report; add the feature-set delta to the architecture dependency note).
- N5 (design note): `resolve_validated` returns all answers with no cap or ordering; A-3b should bound the address count and preserve resolver order for Happy Eyeballs. IPv6 answers on an IPv4-only host are validated but may be unroutable; not a security issue.
- N6 (evidence hygiene): bench-product idle RSS 2.65 MiB is the skeleton, not the product; do not cite it as G0/G4 evidence for the fetch path. Per-fetch delta and concurrency (semaphore, E-2) remain unmeasured; the 10% / 40 MiB fidelity bound in ADR-003 applies from A-3b.
- N7 (`a3b_merge_gate` enforcement): D-7's required-check list still names only fmt/clippy/test/deny/release-guard; a test inside `cargo test` is not separately required. Sprint plan says a required check runs it by name; add a dedicated job id (or state that `test` covers it) in ci-branch-protection.md when A-3b lands. Not needed for this sprint.
