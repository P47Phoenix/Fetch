# A-1 Spike Report: rmcp stack, memory, aarch64 cross-build

Status: DONE. Measurements are x86_64 ONLY (Intel Core Ultra 9 275HX, Linux 7.2, glibc). NO native aarch64 measurement was made (no access to the ARM cluster runner; none was assumed).
Code: `spikes/a1/` (throwaway cargo project). Raw results: `spikes/a1/bench/results-x86_64*.jsonl`.

## 1. Versions verified (crates.io via `cargo search`, Cargo.lock)
rmcp 3.4.0 (+rmcp-macros 3.4.0), tokio 1.53.1, reqwest 0.13.5, hyper 1.11.1, hyper-util 0.1.20, hyper-rustls 0.27.9, rustls 0.23.45 (ring), ureq 3.4.2, htmd 0.5.5, html2md 0.2.17, html2text 0.17.1, lol_html 2.9.0, mimalloc 0.1.52. rustc/cargo 1.94.1.

rmcp 3.4.0 stdio server API (read from crate source/README in the cargo registry; Context7/WebFetch were not used):
- Features needed: `server`, `transport-io`, `macros`, `schemars`.
- `#[tool_router(server_handler)] impl S { #[tool(description=..)] async fn fetch(&self, Parameters(p): Parameters<P>) -> Result<String,String> }`, then `S.serve(rmcp::transport::stdio()).await?.waiting().await?`.
- `P` derives `serde::Deserialize` + `schemars::JsonSchema`. Minimal server compiled first try; `initialize`, `tools/list`, `tools/call fetch` verified over stdio by `bench/measure.py` (real HTTP GET, all 10 runs per combo returned success).
- FINDING: tool futures must be `Send`, even on a `current_thread` runtime. Non-Send state (Rc/RefCell, lol_html default local handlers) held across `.await` fails to compile. Fix used: `lol_html::send::{HtmlRewriter, Settings}` with `Arc<Mutex<..>>`.

## 2. Build profile
`opt-level="s"`, `lto=true`, `codegen-units=1`, `panic="abort"`, `strip=true`; tokio with `default-features=false`, features `rt,macros,io-std,io-util,net,time`, runtime `#[tokio::main(flavor="current_thread")]`. reqwest `default-features=false` + `rustls-no-provider` + rustls `ring` provider installed at start (avoids aws-lc C build). Tool: one `fetch` tool (url, max_length, start_index, raw).

## 3. Measured results (x86_64, median of 10 runs each)
Method: fixture = 5,243,433 byte HTML (generated by `bench/gen_fixture.py`, served by `bench/serve.py`, plain HTTP on 127.0.0.1, no compression). Idle = VmRSS after `initialize` + `tools/list` + 0.5 s. Peak = VmHWM (/proc/<pid>/status) after one `fetch` (max_length=50000, start_index=0). Body cap 16 MiB. kB values.

### Reading the numbers
- Idle is 3.7-5.2 MB for every non-mimalloc combo: comfortably under 10 MB. HTTP client choice moves idle by about 1 MB and peak by about 1 MB; it is not the deciding factor.
- Buffered HTML->markdown with a DOM converter (htmd, html2md) costs about +41 MB over the raw-body baseline, giving 56 MB peak: FAILS the 40 MB target. html2text is far worse (185 MB).
- The 5 MB body itself costs about 10 MB (body Vec + String; growth by doubling). With `String::from_utf8` (no lossy copy) the raw path is about 14-15 MB.
- Streaming with early stop (page-sized output) gives 6.1 MB peak; even a deep page that must scan most of the body gives 8.7 MB. Both far under 40 MB.
- mimalloc raised idle to about 11 MB (over the 10 MB target) and peak by 6-17 MB. It is a regression here; use the system allocator.
- Caveats: html2md and htmd showing near-identical peaks is measured, not verified further (both build a full DOM). The streaming markdown emitter is a crude spike (headings/lists/paragraphs only; entities not decoded; links/emphasis/code/pre dropped), so real conversion quality and its memory cost are NOT proven. Single synthetic fixture. Real TLS handshake, HTTP compression (gzip/br disabled here), redirects, and non-UTF-8 charsets were NOT exercised. Buffered numbers in 3a are what a naive design costs; 3b is a lower bound for a streaming design, not a finished one.

## 4. aarch64 cross-build (proven from this x86_64 host)
No aarch64 gcc, clang, `cross`, or zig was preinstalled. `rustup target add aarch64-unknown-linux-gnu aarch64-unknown-linux-musl` works (rust-std only; no linker or C compiler, so plain `cargo build --target` cannot link and cannot build `ring`).

Method that works (both targets, exit 0, about 35 s each):
```
pip install --user ziglang            # ziglang 0.16.0 (provides `zig cc`)
cargo install cargo-zigbuild          # 0.23.4
export PATH=$PATH:$(python3 -c "import ziglang,os;print(os.path.dirname(ziglang.__file__))")
cd spikes/a1
cargo zigbuild --release --target aarch64-unknown-linux-gnu.2.17 --features http-reqwest,conv-lolhtml
cargo zigbuild --release --target aarch64-unknown-linux-musl     --features http-reqwest,conv-lolhtml
```
Results: gnu binary 2,957,304 B (ELF aarch64, PIE, dynamic, glibc 2.17 floor via `.2.17` suffix); musl binary 2,904,584 B (ELF aarch64, statically linked, stripped). `podman` exists on the host but was not needed or tried.

qemu-user: `qemu-aarch64-static` 10.2.2 is installed and binfmt is active.
- The musl static binary runs and works under qemu: full MCP handshake and a real fetch succeeded (`all_ok` true). The gnu binary cannot run here (no aarch64 glibc loader/sysroot: `/lib/ld-linux-aarch64.so.1` missing).
- RSS from qemu is INVALID for the targets: /proc/<pid> reports the qemu process, including its translator and JIT overhead (measured idle 13.0 MB, peak 19.5 MB for the musl binary versus 4.7/6.1 MB native x86_64). Do not cite these as ARM results.

## 5. Must still be measured on the native aarch64 runner
1. Idle VmRSS and peak VmHWM (median of 10) for the recommended binary, both gnu and musl builds; page size (4K vs 16K/64K on some ARM kernels) can shift RSS.
2. musl malloc versus glibc malloc RSS/fragmentation and latency on a 5 MB and 50 MB fetch (musl allocator is a known risk for peak memory and speed).
3. Real HTTPS fetches (ring on aarch64, rustls cert verification via rustls-platform-verifier needs system roots present on the runner; consider webpki-roots for a static musl image).
4. Compressed responses and 50 MB boundedness once implemented.
5. The E-1 incumbent baseline on the same runner (ratio targets are relative).

## 7. Risks
- R1: DOM-based converters (htmd/html2md/html2text) cannot meet the 40 MB peak on a 5 MB page; a streaming converter is required. Measured 56 MB and 185 MB.
- R2: A production streaming converter (lol_html or html5gum/html5ever tokenizer plus custom markdown emitter) is real work: entity decoding, links, emphasis, code/pre, tables, readability-style main-content extraction (which normally needs a DOM). Quality vs the incumbent is unproven. `raw=true` and non-HTML fall back to about 11-14 MB buffered, still within target for 5 MB but the 50 MB case (E-4) needs a streamed/capped raw path.
- R3: rmcp requires Send tool futures (lol_html must use its `send` API); rmcp is at a new major (3.x), so API churn is possible, pin exact version.
- R4: ring/rustls builds need a C compiler (zig cc solved it for cross builds; CI needs zig or an aarch64 runner). aws-lc (reqwest default) is heavier and was avoided.
- R5: musl allocator behavior and page-size effects on ARM are unmeasured.
- R6: Measurements used one synthetic fixture over plain HTTP; peak under real pages, TLS and compression will be higher.

## 8. Recommendation
Stack: rmcp 3.4.0 (stdio, `tool_router`), tokio `current_thread` (rt, io-std, net, time only), reqwest 0.13 (`default-features=false`, rustls with ring provider) for ergonomics, redirects, proxy and gzip; hyper+hyper-util+rustls is a viable smaller alternative (about 1.1 MB smaller binary, about 1.3 MB lower peak on buffered raw) if binary size matters, but the difference is small versus the conversion cost. ureq is sync and needs spawn_blocking with rmcp; not preferred. Converter: streaming push tokenizer (lol_html 2.9 via its `send` API, fed reqwest chunks with early stop once start_index+max_length chars are produced); do NOT use htmd/html2md/html2text on the whole body. System allocator, not mimalloc. Ship gnu (`.2.17`) and static musl builds via cargo-zigbuild, decide on ARM measurements.

## 9. Preliminary go/no-go (x86_64 only, ARM not measured)

| Idle VmRSS <= 10 MB | 4.6 MB (streaming build); 3.7-5.2 MB all non-mimalloc builds | GO (preliminary) |
| Peak VmHWM <= 40 MB on 5 MB page | Streaming 6.1 MB first page, 8.7 MB deep page, 11.1 MB raw; buffered DOM 56 MB (fail) | GO only with streaming design; NO-GO for a buffered DOM converter |

Overall: conditional GO on the memory case, pending native ARM measurement (section 5) and a real streaming converter meeting quality parity (R2). This verdict is x86_64-only.
