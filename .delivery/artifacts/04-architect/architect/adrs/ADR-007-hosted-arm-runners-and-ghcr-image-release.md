# ADR-007: GitHub-hosted native runners (arm64 and amd64) for the memory gates, and a multi-arch GHCR container image as the release artifact

Status: Accepted (user decisions, 2026-09-19 session, including the later multi-arch decision). Amends ADR-005; supersedes the runner and binary-matrix parts of architecture.md 9 as it stood before this ADR.
Date: 2026-09-19

## Context
The plan assumed (a) a self-hosted native aarch64 runner on the author's Raspberry Pi 5 cluster (OQ-9) to measure memory (gates G0, G4a, G4b, E-5, D-1 re-measure, E-6), with an ephemeral, no-credential, LAN-isolated trust model (architecture 9.2), and (b) release artifacts as standalone binaries (aarch64 gnu.2.17, aarch64 musl candidate, macOS arm64, best-effort x86_64) with checksums (D-2). The user has now decided both points explicitly. The repository is public, so GitHub-hosted arm64 runners (`ubuntu-24.04-arm`) are available; everything can then be done on GitHub.

## Decision
1. **Where the native aarch64 memory measurement runs:** GitHub-hosted arm64 runners (`ubuntu-24.04-arm`, public repo). No self-hosted runner. The hosted runner is a cloud VM, not the Pi 5 cluster. Each report records OS, kernel, CPU model, RAM, `getconf PAGESIZE`, THP setting and cgroup/container flags. The same applies to amd64 on `ubuntu-24.04` (see decision 4). The absolute targets are unchanged: idle VmRSS <= 10 MB, peak VmHWM <= 40 MB on the 5 MiB fixture, median of 10 valid runs (MB and MiB as defined once in E-1). No concrete reason to change them was found; the caveats below are flagged for the user, not decided.
2. **Release artifact:** a tested container image published to GHCR (`ghcr.io/<owner>/<repo>`) from GitHub Actions only. Standalone gnu/musl/macOS binary releases and per-binary checksums are dropped from D-2. The image is tagged and published only after the ARM gates pass on that exact image, identified by digest: the digest that is tested is the digest that is published (promotion adds tags to that digest; it never rebuilds).
3. **Ordering constraint (does not decide OQ-7):** publishing a public image is a distribution act. OQ-7 (licence and distribution) must be answered before the first image is published. Until then candidate images exist only as private, untagged digests in GHCR (or as CI artifacts). OQ-7 stays OPEN.
4. **Platforms (added by the user later the same day): the image is published for `linux/amd64` and `linux/arm64` as a multi-arch manifest.** Both have free native GitHub-hosted runners (`ubuntu-24.04`, `ubuntu-24.04-arm`), so BOTH platforms are hard-gated on native memory measurements (idle <= 10 MB VmRSS, peak <= 40 MB VmHWM, median of 10 valid runs; MB/MiB unit as defined once in E-1). This covers Linux, macOS via Docker Desktop and Windows via WSL2. Considered and DEFERRED (not rejected, out of initial scope): Windows containers, `linux/arm/v7`, `linux/386`, `linux/riscv64`, `linux/ppc64le`, `linux/s390x`.
5. **Policy for a future platform we can build but not natively memory-verify:** it may be published only if clearly labelled "memory targets not verified on this platform" in the image description/labels (`org.opencontainers.image.description` and a dedicated annotation) and in the docs. QEMU results never count as a gate. amd64 and arm64 stay hard-gated; the release is blocked unless BOTH platform gates pass.

## Alternatives considered
| Option | For | Against | Verdict |
|---|---|---|---|
| A. Self-hosted Pi 5 runner (previous plan) | Real target hardware, real Pi page size and CPU, full control (governor, load) | Trust model (ephemeral, no credentials, LAN isolation), availability depends on the home cluster, manual fallback, provisioning work in Sprint 3, risk for the user's protected hosts | Rejected by the user |
| B. Both (hosted for gates, Pi as extra confirmation) | Extra fidelity | Two measurement environments to keep comparable; keeps the trust model alive; user said no self-hosted runner | Rejected as a standing setup. A one-off manual Pi 5 run remains available to the user at any time, informational only and not a gate (see risks) |
| C. Standalone binary releases (gnu/musl/macOS) plus hosted measurement | Smallest install for users without a container runtime; macOS native | Measured artifact is a bare binary while users may run it elsewhere; three-target matrix, ad-hoc codesigning, checksums, glibc floor concerns; more release surface | Dropped from D-2 by the user |
| D. Tested multi-arch (amd64 + arm64) image on GHCR (chosen) | One artifact, one measured thing, digest gives an exact tested-equals-published guarantee, GitHub-only, provenance/SBOM attestations are native to the registry | Two hard memory gates to keep green (double the measurement matrix, though both run on free native runners); users need a container runtime (Docker/Podman) to run a stdio MCP server (`docker run -i --rm`); process start goes through the runtime; macOS users run the linux/arm64 image in a VM; package visibility must be handled (see risks) | Chosen |

## Consequences
+ The trust model shrinks: hosted runners are ephemeral VMs the project does not own, with no route to the user's LAN. The self-hosted-only rules (ephemeral registration, no LAN route, protected-asset isolation, label-gated PR runs, maintainer-only dispatch on self-hosted) are removed. Kept: least-privilege `GITHUB_TOKEN` (default `contents: read`; `packages: write`, `id-token`, `attestations` only in the publish job), no `pull_request_target`, all actions pinned by commit SHA, no secrets on fork PRs.
+ ARM jobs can run on same-repo PRs (no manual label needed) because they cost nothing on a public repo; the per-PR aarch64 test job (D-3) and memory gate (E-6) become cheap. Fork PRs run the same hosted jobs with no secrets and never push an image.
+ The measured object is exactly what users pull, per platform, and the manifest list that references both per-platform digests is itself gated. FR-15 is checked on the image contents.
- Runner availability replaces "offline runner": GitHub Actions or arm64 runner-pool outage or queueing blocks the gates and therefore the release. Skipped is still failure (required checks).
- The hosted VM has variable neighbours and possibly different CPU generations between runs. VmRSS and VmHWM are per-process counts of touched pages and are insensitive to CPU speed, so the memory gates are expected to be stable; latency figures (NFR-02 p95) are recorded, and must not be gated on hosted runs.
- There is no longer a "manual run on the same runner" fallback. The only accepted fallback is re-running the workflow (`workflow_dispatch`) against the same image digest. A local or Pi run is informational.
- FR-15, US-8, NFR-06, NFR-13, NFR-15 and the D-4 install guide need re-wording (image instead of binary, no macOS-native or standalone artifact); see the ADR-007 report.
- ADR-005 amended (below).

## Image design (summary; detail in architecture.md 9.3)
- Base: minimal, non-root, pinned by digest. Musl flavour: `gcr.io/distroless/static-debian12:nonroot` (or `scratch` plus a numeric non-root `USER`). Gnu flavour: `gcr.io/distroless/cc-debian12:nonroot`. No shell, no package manager, no CA bundle needed (roots are embedded, ADR-001).
- Platforms: `linux/amd64` and `linux/arm64`, published as one manifest list built from per-platform images. Each per-platform image is built and measured on its native hosted runner. The amd64 baseline is no longer the "x86_64 only preliminary" spike figure (A-1 measured Intel/glibc/plain HTTP): it is a real gated measurement. Deferred platforms are listed in decision 4; unverified-platform policy in decision 5.
- The `bench-loopback` build is a second image target (same Dockerfile, same base digest, same commit and Cargo.lock hash). It is never pushed to a registry and never tagged; it lives on the runner or as a short-lived CI artifact.
- Digest flow: (1) per-platform build jobs (native runner each, buildx) push a private untagged image by digest and output its digest D_amd64, D_arm64; (2) a merge job creates the manifest list M from those two digests (`docker buildx imagetools create`, untagged, private) and outputs the manifest digest M; (3) per-platform test jobs on the matching native runner pull `@sha256:M` with the platform selected, assert the resolved platform digest equals that platform's D, and run handshake, `--version`, feature guard on the extracted binary, FR-15 checks and the memory gates; (4) only if BOTH platform test jobs pass, a publish job adds tags to M (`imagetools`/`crane tag`, no rebuild) and attests provenance/SBOM. The digest measured is the per-platform digest that is published, and the manifest digest that references them is the one tagged. The publish job `needs:` both platform gates; skipped is failure. Attestation manifests, if buildx adds them to the index, must be part of the M that is tested and tagged.

## Libc and allocator inside the image (resolves the open question cleanly)
- Allocator: unchanged, system allocator (ADR-005).
- Libc (one flavour for both platforms, chosen on the worse platform; if amd64 and arm64 disagree, flag it to the user): the reason for shipping `gnu.2.17` as primary was compatibility with unknown host glibc versions. Inside an image the host libc is irrelevant, so that reason disappears, and ADR-005 criterion 2 already prefers musl (static, strongest FR-15) when parity holds. Recommendation: the image ships exactly ONE flavour, chosen by the unchanged ADR-005 criteria 1-5 on the hosted arm64 runner, measured inside the image. Until G4a both candidate images are built and measured; one is published. Expected outcome: musl static on distroless/static if parity holds, otherwise gnu on distroless/cc. This needs no user decision unless the data leaves both flavours failing or within noise of each other (then the tie-break stays the ADR-005 preference order). The `gnu.2.17` glibc floor loses its purpose for the image; whether to drop the zig `.2.17` suffix and build gnu natively on the arm runner is a developer choice, not an architecture decision, provided the same pinned profile and the FR-15 symbol check still apply.
- Note for musl in a container: DNS goes through the runtime resolver (`/etc/resolv.conf` injected by Docker/Podman), so `.local` and split-DNS behaviour depends on the runtime, not the image. The ADR-005 `.local` criterion must be tested from inside the container on the hosted runner, and the limitation documented for home-lab users.

## Measuring a process inside a container
- The gate reads `VmRSS` and `VmHWM` from `/proc/<pid>/status` of the server process itself, not container-level accounting (`docker stats`, cgroup `memory.current`), which include page cache and are not comparable to the targets. The server runs as the container's PID 1 with `docker run -i` (no init wrapper, so there is no extra process); the harness reads the host-visible pid (`docker inspect -f '{{.State.Pid}}'`) or `docker exec`-free equivalent, and the report records which. The harness process, MCP client script and fixture server run outside the container.
- cgroup memory limits do not change VmRSS/VmHWM of a process that stays under the limit; they only add an OOM kill above it. The gate runs with no memory limit, and a second confirmation run with a 64 MiB (`--memory=64m`) limit must pass without OOM to show real headroom (recorded, not the gate). Page cache for the image layers is charged to the cgroup but is not in VmRSS (file-backed pages the process maps count in RssFile, same as outside).
- The container runtime's own processes (dockerd, containerd-shim, runc) are not part of the server RSS and are excluded; this must be stated in every report.
- QEMU and emulated builds are still invalid for measurement: the harness preflight adds `uname -m` inside the container, must not use `docker/setup-qemu-action` on the measurement job, and asserts no aarch64 binfmt handler.

Status line becomes: "Proposed; amended by ADR-007". Superseded: "primary release artifact = `aarch64-unknown-linux-gnu.2.17` (dynamic ...)" and "macOS arm64 uses the platform allocator", "author's native aarch64 runner" (now the GitHub-hosted arm64 runner), and the standalone-binary framing of "ship both and let the user choose" (option 4 is now: build both candidate images, publish one). ## Risks the user should know
1. GHCR packages are private by default when first pushed by a workflow. Making the package public is a manual setting (package settings, or inherited from the repository when linked by the `org.opencontainers.image.source` label; verify this behaviour before relying on it) and is exactly the distribution act OQ-7 must precede. Anonymous `docker pull` fails until it is public.
2. Hosted arm64 runners are Arm cloud VMs; the CPU, kernel and page size will differ from the Pi 5 cluster. Ubuntu arm64 hosted kernels are normally 4 KiB pages; Raspberry Pi 5 kernels default to 16 KiB pages, which can inflate RSS. A pass at 4K does not prove a pass on a Pi. Targets are left unchanged (per the user); this is flagged, and the user may run the image once on a Pi 5 for information. Whether targets should then be restated per page size is a user decision, not made here.
3. Runner variability: different VM hosts nightly; record CPU model per run; median of 10 valid runs within one job on one VM; latency not gated.
4. Runner background load (runner agent, other services) makes the "load average within 0.5 of idle baseline" rule noisier than on a dedicated host; the rule should be recorded and applied, with the baseline measured in the same job.
5. Hosted-runner availability and Actions quotas: standard arm64 runners on public repositories are free at the time of writing, but this is a GitHub policy, not a contract; verify at the start of Sprint 3 and record.
6. The user (and any consumer) needs a container runtime; stdio MCP through `docker run -i` adds startup latency (NFR-02 readiness 250 ms figure from Sprint 1 must be re-stated for image start, and is a story change for the developer).

6. amd64 hosted runners are cloud VMs on varying x86 CPU models (Intel/AMD); page size is 4 KiB, matching typical desktops and Docker Desktop VMs, but it does not represent every host. Record the CPU model per run. The two platforms are compared only to themselves, never averaged.
7. macOS via Docker Desktop and Windows via WSL2 run the image inside a Linux VM; the process RSS measured on native Linux runners is the claim, VM overhead is outside it and should be stated in the docs.
